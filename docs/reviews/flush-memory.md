# Code review: phase4/flush-memory (6de44d7)

Reviewer: code reviewer (fresh context). Branch `phase4/flush-memory` at `6de44d7` (base `55453ae`; main has moved by docs only, so main's code is the base). Worktree `strata-wt/flush-memory`. Ledger `docs/status/flush-memory.md`, perf record `docs/perf/peak-memory.md`. HEAD equals `origin/phase4/flush-memory`. CI on 6de44d7 (run 39557337899): all eight jobs green (freebsd-x86_64, linux-asan-ubsan, linux-x86_64-gcc, linux-tsan, linux-x86_64-clang, macos-x86_64, linux-arm64-gcc, macos-arm64).

## Verdict: APPROVE WITH CONDITIONS

The lifetime design holds from the first pin to the end of the flush, for every caller the index's one-owner contract allows: from the pin on, no probe made a lease or a view outlive or see a changed buffer (ASan+UBSan 25/25, TSan 25/25, and my probes with zero TSan reports), main's bytes are reproduced in 192 flush shapes, and no failure I injected left a file or a published segment. Two misuse paths are not covered and I can demonstrate both: a mutation before the per-run pin is a heap-use-after-free (CR2), and `close()` inside a flush half-resets the index and loses durable documents (CR3). Neither is reachable by a conforming caller. A third item is a contract this change made false (CR1): the run threads now drive `File`, a cross-library question I cannot settle by a probe; it goes to the architect, and matters only for `flush_threads > 1` on a non-POSIX IO.

Blocking items: none. Conditions: CR1 (comment fix before landing; architect ruling before `flush_threads > 1` is used on a non-POSIX IO), CR2 and CR3 (fix in this round, each a few lines, or record as owed with an owner).

## Findings

### CR1 (condition, architect for the contract): run threads now drive `File`, and the option's comment says they do not

`index.hh:381` (`flush_threads`) still says "Files, ids, and accounting stay on the owner thread". After this change they do not: `stream` (`index.hh:2159-2185`) runs on the run threads and writes through `file_sink` into a `File` the owner created (`index.hh:2196`); only creation, `track`, mapping and publication stay on the owner. Before, run threads only inverted and encoded, and the owner wrote (`write_unsynced`). The `File`/`IO` interface (`completion/io.h:73-94`) says nothing about thread affinity, and its sibling comments ("a retained worker-side original") suggest a backend may bind a file to a context. POSIX and faultfs are fine (ASan, TSan clean, including `flush_memory_test` with three runs and `cross` below). The contract is the open part, and a probe cannot settle what a host IO other than POSIX promises.
- Fix now: correct the comment at `index.hh:381` and say in `core/` docs that with `flush_threads > 1` a flush calls `File::write_at` from its run threads, one thread per file.
- Architect: rule whether an IO's `File` may be written off the creating thread, or whether run threads should hand bytes back (the old memory cost) or the IO must say so. Until ruled, `flush_threads > 1` stays unrecommended on a non-POSIX IO. At `flush_threads == 1` everything runs on the owner thread, as before.

### CR2 (condition): the pin comes after the pointers it protects, so the window "whatever else runs" is not closed

`flush_documents` collects `docs` (pointers into `buffer_`, `index.hh:2130-2133`), sorts it, creates the files (`index.hh:2196`), starts the threads, and only then does each run take its pin (`index.hh:2166`). A mutation in that window is not refused. Probe `probe_lifetime.cc early` (a second thread applies 3,000 documents while the owner is inside `create_exclusive`, before any pin): AddressSanitizer reports heap-use-after-free, read in the run lambda of `flush_documents`, the block freed by `buffer_.push_back` reallocation in the other thread's `apply` (`.scratch/review/round3.out`). Calling `apply` from another thread breaks the index's one-writer contract anyway, so this is not reachable by a conforming caller, and the same thread cannot reach it without a callback. But the ledger and `peak-memory.md` state the guarantee as "cannot change under the writer, whatever else runs", and `borrow.hh:1-5` as "the views cannot dangle", which is only true from the pin on. The `docs` vector is the same kind of view as the stored records and the keys.
- Fix: take one lease in `flush_documents` on the owner thread before building `docs`, keep it to the end of the function (its destructor releases it on any exit), and keep the per-run pins; the owner's lease makes the whole function refuse mutation, and the per-run pins stay what hand a lease to each builder. Or state in `borrow.hh` that the gate is a tripwire for the stream, not a lock. Either closes the finding; the first is three lines.
- Related, same cause: `require_unpinned` and the pin are separate atomic steps, so a mutator that checks just before a pin and writes after it races. Only a second thread can do that. A real cross-thread guard needs a lock; the one-writer contract is what the design stands on, and `borrow.hh` should say so.
- Probe `cross` (second thread applies while a run thread is mid-write, pool executor with merges queued, one and three runs): the other thread's `apply` threw the gate's `logic_error` at `push_back`; TSan reported nothing; the index finished complete and writable (`.scratch/review/probes.out`). The pool's background merges never reach `buffer_` (`grep buffer_` in `index.hh`: only digest, rollback, apply, accessors, flush, `clear_buffer`).

### CR3 (condition): `close()` is not atomic against the gate, and half-closes into silent data loss

`close()` (`index.hh:481-493`) resets `group_`, empties `pending_` and `segs_`, and only then calls `clear_buffer()`, whose `buffer_.clear()` throws while a lease is held. Probe `probe_lifetime.cc close2`: `close()` called from inside a flush (one and three runs) after 300 documents were durable. `close()` throws the gate's `logic_error` with `segs_` already cleared and `fenced_` not set; the flush fails and removes its files; the index then accepts a write, and the next `commit()` succeeds with a manifest that no longer names the 300 durable documents (`find_key("Q0")` is false, live count 301 against 300 + 1 expected). Before this branch the same call was a use after free; now it is a deterministic half-close. A conforming caller never calls `close()` inside a flush, so this is a misuse path, but the outcome is data loss, not a refusal, and the fix is one line.
- Fix: make `close()` (and any other multi-step reset) call the gate first (`buffer_.clear()` before the other resets, or an explicit `require_unpinned()`), so a refused close changes nothing. Add the probe's shape to `flush_memory_test` (close inside the flush, then the index still holds its durable documents).
- Same shape, harmless: `apply` from the IO hook (probe `reenter`) throws from `buffer_.push_back` after `bump_last_docid` and `set_buffered_docid` have run (`index.hh:1938-1943`), with no rollback. The probe shows the index still complete and writable afterwards (the stray docid-map entry dies with `clear_buffer`; `last_docid` keeps a gap). Order the gate check before the side effects if that is cheap; not required.

### CR4 (non-blocking, the author's two gaps): `reserve` is observed nowhere above the stored builder; no per-item revert check was done

I reverted each item on a copy of `include/` (`.scratch/review/mut/run.py`, never the tracked files) and ran `flush_memory_test` with ASan+UBSan. Survived (the test passes without the code):
- `w.reserve(...)` removed from `flush_documents` (`index.hh:2177`): the author's known gap, confirmed.
- `docids_.reserve(docs)` removed from `basic_segment_writer::reserve` (`writer.hh:432`), and the call into the builders (`writer.hh:433`) removed: the unit test reaches only `stored_builder::reserve`.
- `stored_size()` returning 0 (`index.hh:987-993`): the hint's total is never checked, and the borrowing path does not use it.
- The directory sync after the failure cleanup removed (`index.hh:2212`).
- The footer CRC left out of the mapped segment's ref (`index.hh:1127`): `flush_memory_test` never reopens; the reopen tests elsewhere cover it, I did not run that mutant against them.
Killed: reserve no-op in the builder, borrow no-op, gate no-op, pin dropped (the author's), `owns()` always true, failure cleanup removed, ENOSPC no longer mapped to `space_error` (the index fences instead: a real check of the ENOSPC contract), borrowing on run 0 only. `track()` dropped survives `flush_memory_test` but is killed by `index_test.cc:426` (storage admission, run against the mutant). `charge.shrink` removed and the read-back charge removed survive; both are accounting that the settle returns anyway, so I count them equivalent for the budget's end state.
- A test that would observe `reserve` at the writer and index levels: a writer-level twin of `reserve_allocates_once` over `basic_segment_writer` (charge constant after the first `add` with the hint, growing without it), and in `writer_holds_no_copy` a bound tight enough to tell exact-capacity from doubled capacity (the charge is capacity based, so 600 documents reserved is 600 slots against 1,024).

### CR5 (non-blocking): the mapped segment is no longer compared with what was written

The old `written_segment` accepted a mapping only if its footer CRC equalled the CRC of the in-memory bytes (`index.hh:1115-1117`, still used elsewhere). `streamed_segment` (`index.hh:1124`) takes the footer CRC from the mapping and checks only that the mapping's size equals the bytes streamed. The single-run inverter flush already worked this way, so this extends an existing choice to the multi-run flush rather than adding one; a corrupted page-cache view of a just-written file would now be recorded as the file's truth. The manifest's recorded CRC is checked at open against the file, so a flush-time fault is caught when the index reopens, not at flush. Say so in the design or accept it.

### Notes, none blocking

- `std::vector<std::thread>` in `flush_documents` (`index.hh:2198-2201`) terminates if a thread cannot be created part way (joinable threads destroyed). Unchanged from main. It also is a second thread mechanism beside Kronuz/threadpool, which `calibration.md` row 1 asks to be a finding; it is main's (D18), not this branch's.
- The publish loop (`index.hh:2224-2230`) can still fail after the first segment is emplaced (a failed map, read-back, or footer decode), leaving some runs published and the buffer kept. Same as main's loop. The comment "a write that fails publishes none" holds for writes only.
- Compatibility with phase4/kv-scan: no conflict with the lease design. Its buffer view holds buffer indices and reads `buffer_[i]` through the const accessors (`git diff 55453ae..phase4/kv-scan`), which `borrowable_vector` keeps. `git merge-tree` of the two branches conflicts only in `CMakeLists.txt` (adjacent test registrations); `index.hh` merges clean (I did not compile the merge). The scan should not use a lease to guard cursors: `apply` throws after side effects (CR3's note), so the gate is a poor cursor guard; its mutation counter, as that design says, is the right tool.
- Move of the index while a lease is held ends the process by design (`probe_lifetime.cc move`: `libc++abi: terminating`); a moved vector keeps its element addresses, so the terminate is conservative.

## Checks against the lead's list

1. A lease or view alive while the buffer mutates or frees: the type refuses every mutator (`push_back`, `pop_back`, `clear`, `at_mut`, `back_mut`) from the first pin (`borrow.hh`), reads are const-only. An exception mid-flush releases the lease and the views with the writer (RAII; probes `throw` with `runtime_error` and `bad_alloc` at the 1st, 2nd and 3rd write, one and three runs: buffer unpinned, files removed, retry complete). Gaps: before the pin (CR2), and `close()` (CR3). Reentrant `apply`, `close()` and cross-thread `apply` all refused at the gate once pinned. Move: terminates. A scan's view: compatible (note above).
2. Failure atomicity: every injected failure left no segment file and no published segment: ENOSPC and EIO at write, an arbitrary exception at the 1st/2nd/3rd write, ENOSPC at the creation of the 1st, 2nd or 3rd file (`create_enospc`: surfaces as `system_error` ENOSPC, not fenced, retry succeeds). ENOSPC stays a `space_error` inside and a plain ENOSPC `system_error` after `guarded`, as before. `commit_files` and its sync, rename and manifest order are not in the diff. The new behaviour is that non-ENOSPC failures now also remove the files (main left them for the orphan sweep).
3. Byte identity with main: `probe_identity.cc` (192 shapes: 1, 2, 3 and 5 flush threads, `flush_min_docs` 1 and 40, random, repetitive and random-byte values, deletes, keyless documents, 70 KB values, with and without a budget, `zstd_merged`, `force_merge`) built against the branch and against main's headers (`git archive 55453ae include test`): identical output, plain and under `STRATA_FAULTFS_MAP=1`. This covers the cases the two pinned digests do not.
4. The author's gaps: CR4.
